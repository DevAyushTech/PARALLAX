# PARALLAX — frontend/backend integration contract

This document describes the running FastAPI implementation, not the earlier planning sketches. Canonical JSON fields and endpoints below are the frontend integration contract for the MVP. No frontend files were changed for this handoff.

## Local setup and CORS

From the repository root:

```bash
python3 -m pip install -r backend/requirements.txt
PARALLAX_CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173 \
  PYTHONPATH=backend python3 -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Use an existing virtual environment where available; see `README.md` for exact setup commands. Backend settings load the repository-root `.env` if present; environment variables take precedence. The database defaults to `sqlite:///./parallax.db`, relative to the server's working directory; `PARALLAX_DATABASE_URL` overrides it. Do not delete an existing database to change configuration.

Frontend configuration already present in `frontend/.env`:

```text
VITE_API_BASE_URL=http://localhost:8000
```

The base URL must **not** include `/api`: the frontend API client appends it. Vite environment changes require a dev-server restart.

Backend CORS (`backend/app/config.py`, `backend/app/main.py`):

- Default allowed origin: `http://localhost:5173`.
- `PARALLAX_CORS_ORIGINS` accepts comma-separated exact origins.
- `http://127.0.0.1:5173` is a different origin; add it explicitly if used.
- Allowed methods: `GET`, `POST`. Middleware handles `OPTIONS` preflight automatically.
- Allowed request headers: all, including `Content-Type`.
- Credentials: disabled. Do not enable Axios `withCredentials`; no authentication is needed.
- No wildcard origin is required. A Vite fallback port such as `5174` must be explicitly allowed.

Interactive API documentation: `http://localhost:8000/docs`.
Machine-readable authoritative schema: `http://localhost:8000/openapi.json`.

## Exact endpoint list

All request/response bodies are JSON, unless no request body is indicated.

| Method | Path | Request | Success response |
| --- | --- | --- | --- |
| GET | `/api/health` | none | 200: `{ "status": "ok" }` |
| POST | `/api/cases` | `CaseCreate` | 201: `CaseResponse` |
| GET | `/api/cases/{case_id}` | none | 200: `CaseDetail` |
| POST | `/api/cases/{case_id}/evidence` | `EvidenceCreate` | 201: `Evidence` |
| GET | `/api/cases/{case_id}/evidence` | none | 200: array of `Evidence` |
| POST | `/api/cases/{case_id}/analyze` | none (an empty JSON object is also accepted) | 200: `AnalysisResponse` |
| GET | `/api/cases/{case_id}/graph` | none | 200: `EvidenceGraph` |
| GET | `/api/cases/{case_id}/decision` | none | 200: `Decision` |
| POST | `/api/cases/{case_id}/reevaluate` | optional `EvidenceCreate`; omit body to reuse stored evidence | 200: `AnalysisResponse` with audit |

Existing compatibility aliases are retained, not new features:

| Method | Alias | Equivalent |
| --- | --- | --- |
| POST | `/api/decisions` | `POST /api/cases` |
| GET | `/api/decisions/{case_id}` | `GET /api/cases/{case_id}` |
| POST | `/api/decisions/{case_id}/evidence` | `POST /api/cases/{case_id}/evidence` |
| GET | `/api/decisions/{case_id}/evidence` | `GET /api/cases/{case_id}/evidence` |

Use `/api/cases` for new frontend calls. There are no list-cases, agents, jobs, history, authentication, upload, or streaming endpoints. FastAPI also supplies `GET /docs`, `/docs/oauth2-redirect`, `/redoc`, and `/openapi.json`.

## Common data rules

- IDs are UUID strings generated by the backend. Do not send display IDs such as `EV-001` or `CASE-01` as API IDs.
- Enum values are case-sensitive:
  - `status`: `OPEN`, `RESOLVED`, `CLOSED`.
  - `risk_level` and conflict `severity`: `LOW`, `MEDIUM`, `HIGH`.
  - `source_type`: `REPORT`, `SENSOR`, `DISPATCH`.
  - `agent_name`: `PERCEPTION`, `OPERATIONS`, `VERIFIER`.
  - `decision`: `ACT`, `ASK`, `ABSTAIN`.
- Confidence is a JSON number in `0..1`, not a percentage/string. Convert `92%` to `0.92`.
- Text fields must not be blank. Unknown request fields are rejected, not silently discarded.
- Send timestamps with a timezone: `new Date().toISOString()`. Do not send `toLocaleString()` output.
- SQLite currently returns some timestamps without a timezone suffix. These represent UTC. When displaying them, append `Z` if no timezone is present before constructing a JavaScript `Date`. This compatibility behavior is documented rather than changing existing serialization in this task.
- `metadata` is a JSON object and defaults to `{}`.
- Keep `scenario` set to `emergency_bridge_route`. It is currently a non-empty string, not an enum-restricted request field; arbitrary scenarios are not supported by the MVP pipeline.
- Current confidence/freshness thresholds come from backend configuration. The frontend must not choose, recalculate, or hardcode an outcome.

## Requests

### Create a case — `POST /api/cases`

```json
{
  "title": "Bridge B emergency route assessment",
  "scenario": "emergency_bridge_route",
  "status": "OPEN",
  "risk_level": "MEDIUM",
  "initial_evidence": []
}
```

All fields have defaults; `{}` creates an empty fixed-scenario case. `risk_level` defaults to `HIGH`. Creating a case does **not** run analysis. `initial_evidence`, when provided, is an array of up to 50 evidence request objects.

### Add evidence — `POST /api/cases/{case_id}/evidence`

```json
{
  "source_type": "SENSOR",
  "source_name": "bridge_camera",
  "content": "Bridge B is blocked",
  "timestamp": "2026-01-01T12:00:00Z",
  "confidence": 0.92,
  "metadata": {
    "bridge": "B"
  }
}
```

These example timestamps are illustrative; use current observations in a live demo or they will be stale. Required fields: `source_type`, `source_name`, `content`, `timestamp`. Confidence defaults to `1.0`; metadata defaults to `{}`.

Adding evidence stores it only. It leaves the last decision unchanged until analysis/re-evaluation.

Legacy input aliases (`kind`, `source`, `observed_at`, and case `scenario_key`) remain accepted. Prefer the canonical names shown above. Do not send both an alias and its canonical field.

### Analyze — `POST /api/cases/{case_id}/analyze`

No body is needed. The existing `analyzeCase(caseId)` client call is compatible. `{}` is also accepted because this route declares no request-body schema.

The server synchronously runs applicable Perception/Operations claims, then Verifier, validates and stores the analysis, computes conflicts/graph, runs the deterministic gate, and stores the decision. The default unavailable LLM adapter falls back to deterministic mock interpretation.

### Re-evaluate — `POST /api/cases/{case_id}/reevaluate`

Two supported flows:

1. Add evidence using `/evidence`, then call `/reevaluate` **without a body**. The existing `reevaluateCase(caseId)` client call now supports this flow.
2. Send one new `EvidenceCreate` object directly to `/reevaluate`; it stores that item and reruns analysis:

```json
{
  "source_type": "SENSOR",
  "source_name": "camera_current",
  "content": "Bridge B is blocked",
  "timestamp": "2026-01-01T12:05:00Z",
  "confidence": 0.97,
  "metadata": {
    "bridge": "B"
  }
}
```

Do not send `{ "evidence": [...] }` or `{}` to this endpoint. `{}` is an incomplete evidence object and returns 422. Omit the body (or send `null`) when there is no new evidence in this request. Do not first add an item and then send the same item again in re-evaluation: that creates two records.

There is no automatic timestamp replacement, forced conflict resolution, or guaranteed transition to `ACT`. Retained contradictory evidence remains relevant while fresh; the engine applies policy to the new state.

## Responses

### Case creation — `CaseResponse`

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "title": "Bridge B emergency route assessment",
  "scenario": "emergency_bridge_route",
  "status": "OPEN",
  "risk_level": "MEDIUM",
  "created_at": "2026-01-01T12:00:00",
  "evidence": []
}
```

`GET /api/cases/{case_id}` adds `claims`, `conflicts`, `decision`, and `audit` to this shape. Before any analysis, `claims` and `conflicts` are `[]`, `decision` and `audit` are `null`. Case `status` is not a processing-state field and is not automatically updated by analysis.

### Stored evidence — `Evidence`

```json
{
  "id": "22222222-2222-4222-8222-222222222222",
  "case_id": "11111111-1111-4111-8111-111111111111",
  "source_type": "SENSOR",
  "source_name": "bridge_camera",
  "content": "Bridge B is blocked",
  "timestamp": "2026-01-01T12:00:00",
  "confidence": 0.92,
  "metadata": {
    "bridge": "B"
  }
}
```

### Analyze/re-evaluate — `AnalysisResponse`

The envelope is always `{ case_id, claims, conflicts, decision, graph, audit }`; neither a `success` wrapper nor a `data` wrapper is added by the server. `audit` is `null` for initial analysis and populated by re-evaluation. A compact, schema-valid example is below. Graph `data` objects are abbreviated here; runtime nodes include the corresponding evidence/claim/decision attributes.

      "confidence": 0.95,

### Conflict record

`conflicts` is an array, not a single conflict panel object:

```json
{
  "id": "77777777-7777-4777-8777-777777777777",
  "case_id": "11111111-1111-4111-8111-111111111111",
  "claim_ids": [
    "44444444-4444-4444-8444-444444444444",
    "55555555-5555-4555-8555-555555555555"
  ],
  "severity": "HIGH",
  "reason": "Claims disagree on subject 'bridge b': 'blocked' versus 'open'."
}
```

### Decision response — `GET /api/cases/{case_id}/decision`

Returns the `Decision` object directly, the same shape as `AnalysisResponse.decision`:

```json
{
  "id": "88888888-8888-4888-8888-888888888888",
  "case_id": "11111111-1111-4111-8111-111111111111",
  "decision": "ASK",
  "reason": "Material claims conflict, but additional evidence could reasonably resolve it.",
  "risk_level": "MEDIUM",
  "conflicting_claim_ids": [
    "44444444-4444-4444-8444-444444444444",
    "55555555-5555-4555-8555-555555555555"
  ],
  "supporting_evidence_ids": ["22222222-2222-4222-8222-222222222222"],
  "next_evidence_request": "Request fresh independent evidence addressing bridge b.",
  "created_at": "2026-01-01T12:00:01"
}
```

This is an illustrative recoverable-conflict response, not a promise that every conflict becomes `ASK`. High-risk or severe contradictions can return `ABSTAIN`. `next_evidence_request` is populated for `ASK`, otherwise normally `null`.

### Re-evaluation audit

`AnalysisResponse.audit` and `CaseDetail.audit` are `null` until a re-evaluation runs. Thereafter the latest audit is persisted and has this concise shape:

```json
{
  "previous_decision": "ACT",
  "new_evidence": {
    "id": "99999999-9999-4999-8999-999999999999",
    "case_id": "11111111-1111-4111-8111-111111111111",
    "source_type": "SENSOR",
    "source_name": "camera_current",
    "content": "Bridge B is safe",
    "timestamp": "2026-01-01T12:05:00",
    "confidence": 0.9,
    "metadata": {"fresh": true}
  },
  "new_decision": "ABSTAIN",
  "reason_for_change": "Decision changed from ACT to ABSTAIN: Evidence is severely contradictory; critical safety remains unresolved.",
  "created_at": "2026-01-01T12:05:01"
}
```

`previous_decision` is `null` if re-evaluation happens before any initial decision. `new_evidence` is populated with the latest evidence submitted after the previous decision when evidence was added through `/evidence` before a no-body re-evaluation; it is `null` only when no new evidence can be identified. The current `decision.reason`, `conflicting_claim_ids`, `supporting_evidence_ids`, and graph provide the full transparent trace.

### Graph response — `GET /api/cases/{case_id}/graph`

Returns `{ "nodes": [...], "edges": [...] }` directly, the same shape as `AnalysisResponse.graph`.

- Node: `{ id, type, label, data }`.
- Node types: `evidence`, `claim`, `agent`, `conflict`, `decision`.
- Edge: `{ source, target, relation }`.
- Relations: `evidence_supports_claim`, `claim_produced_by_agent`, `claim_participates_in_conflict`, `conflict_informs_decision`.
- Graph IDs are prefixed (for example `claim:<uuid>`), not bare entity UUIDs.
- Nodes can be disconnected when the data has no relationship; do not invent links.
- Before analysis, the graph can contain evidence nodes with no edges; an empty case returns empty arrays.

## Errors

Expected errors use FastAPI's `detail` field. Axios puts this at `error.response.data.detail`.

**404: missing case**, including unknown case IDs on nested routes:

```json
{"detail": "Case not found. Verify the case_id."}
```

**404: known case not yet analyzed**, on `/decision`:

```json
{"detail": "Decision not available. Run analysis for this case first."}
```

Use `CaseDetail.decision === null` to distinguish an unanalyzed case without needing a failing `/decision` request.

**422: malformed JSON/field validation**, example for confidence greater than one:

```json
{
  "detail": [
    {
      "type": "less_than_equal",
      "loc": ["body", "confidence"],
      "msg": "Input should be less than or equal to 1",
      "input": 1.5,
      "ctx": {"le": 1.0}
    }
  ]
}
```

Treat each validation error's `loc` and `msg` as a field message. Additional keys can vary with FastAPI/Pydantic versions. `detail` is a string for HTTP errors and an array for validation errors; handle both.

**405: unsupported method:** `{ "detail": "Method Not Allowed" }`.

**502: invalid specialist output:** the response is JSON, and the previous persisted decision remains unchanged:

```json
{"detail": "Specialist output could not be validated. The previous decision is unchanged. Check the evidence/provider output before retrying analysis."}
```

Fresh evidence submitted directly to `/reevaluate` may already be stored; fetch the case before retrying to avoid duplicate evidence.

**Unexpected 500:** other unexpected errors, including database failures, can still return plain text `Internal Server Error`; handle non-JSON errors safely. The normal unavailable-provider path uses mock claims, not an HTTP failure. Invalid specialist output is an error, not a successful `ABSTAIN` snapshot.

**Network/CORS/server-unavailable:** no usable HTTP response may reach JavaScript. `error.response` can be undefined. Do not replace the last decision with an invented outcome.

## Loading and processing states

There are no job IDs, polling endpoints, websocket events, `202` responses, or server-side `PROCESSING` status fields. Analyze and re-evaluate are synchronous requests.

Suggested client states (local UI state only):

| State | Trigger | Expected behavior |
| --- | --- | --- |
| loading | initial case/graph/decision fetch | show loading until request resolves |
| not analyzed | case has `decision: null` | show no decision yet; analysis is available |
| saving evidence | `/evidence` pending | show saving; keep the last computed decision |
| analyzing | `/analyze` pending | disable duplicate analysis calls; await complete snapshot |
| reevaluating | `/reevaluate` pending | preserve prior snapshot until updated response arrives |
| ready | successful analysis response | replace claims, conflicts, graph, and decision together |
| error | non-2xx/network failure | show error; keep last successful data; clear loading |

`ASK` and `ABSTAIN` are successful decision results, not loading or HTTP error states. `ACT` is a recommendation, not an automatically executed action.

The backend keeps the latest analysis only; evidence is retained, but there is no persisted decision-history API. Re-evaluation generates new claim/decision IDs. Do not mix graph data from old and new responses. Fresh evidence sent directly to `/reevaluate` is committed before analysis; if analysis fails, fetch the case before retrying so the same item is not appended twice. Do not make concurrent analysis/re-evaluation calls for one case: this MVP has no in-progress guard.

## Existing frontend integration handoff

`frontend/src/services/api.js` uses Axios. Successful calls resolve to an Axios response: the backend JSON is in **`response.data`**.

The backend is compatible with its health/create/add/analyze/get/graph/decision URLs and with no-body `reevaluateCase(caseId)`. The UI still needs work by its owning team:

- `App.jsx` currently reads `mockData` and uses a timer to hardcode `ACT`; it does not call the live API client. A mounted UI click is not yet proof of live integration.
- Use the backend case UUID rather than fixture display IDs.
- Map the current evidence form to canonical API keys: `source` -> `source_name`, `claim` -> `content`; map visual/sensor to `SENSOR`, operational/status/map to `DISPATCH`, field/report to `REPORT`.
- Send ISO timestamps and no extra display-only fields (`type`, `freshness`, etc.) in evidence requests.
- Render `decision.decision` (not `action`), `supporting_evidence_ids`, `conflicting_claim_ids`, and `created_at` (not fixture camelCase fields).
- Group `claims` by `agent_name`; `conflicts` is an array. Use backend graph nodes/edges, not static diagram labels.
- There is no `/agents` or `/history` endpoint; derive role panels from the case/analysis response. Any UI timeline is local-only for now.

No frontend redesign, mock-removal, or component edits are included in this backend handoff.
